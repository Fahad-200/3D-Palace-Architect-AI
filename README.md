An abandoned Gothic palace rendered in WebGL — four stories, split-level floor plates, curved stairwells, spiral towers, a vaulted great hall, a chapel, a library, ballrooms, servant quarters, an observatory, and an attic. Every surface, every collision box, every light, every sound trigger was generated by an AI agent operating under harness engineering discipline.

**This is a prototype.** It has known issues, rough edges, and places where the collision resolution leaks into the void. It is a proof of what agentic systems can produce when guided by structured context, architectural constraint, and feedback-driven iteration.

### How 6,268 lines were produced in 20 prompts

The critical constraint: DeepSeek V4 Flash has a **170K token context window** that compacts aggressively once exceeded. Every line of this codebase was generated across 20 discrete sessions, each starting with a compressed architectural summary (`PALACE_STATE.md`) that preserved intent while fitting within the shrinking context. This is a practical demonstration of **context compaction** — a harness engineering technique where long-horizon work is decomposed into bounded sessions, each seeded with a structured state file that encodes what came before.

The agent built the shell first (floor plates, exterior walls), then room by room — foyer, great hall, gallery, kitchen, ballroom, library, chapel, master suite, guest quarters, observatory, attic, basement — with collision geometry, materials, lighting, and audio integrated at each layer. Staircases (curved flights, east tower spiral, library spiral, basement trapdoor steps) were the final architectural element, requiring the most complex collision math.

Only in the final session — after all 19 prior sessions had built the complete structure — was a single debugging pass needed to fix three interrelated bugs:
1. **Box3.setFromObject AABB inflation** — rotated step geometries produced overlapping axis-aligned boxes that merged into impassable walls
2. **Stairwell wall Y-offset error** — enclosure walls sat 2.125m above the floor, letting the player walk underneath into the floor gap
3. **Browser ES module caching** — Chrome aggressively caches `file://` ES module imports; a `?v=2` cache-busting strategy was applied across all 27 files

### Collision System

The collision engine (`collision.js`) is a custom AABB sweep-and-prune grid with three-tier classification:

- **Climbable** (height ≤ 1.0m) — stepped over automatically
- **Medium** (1.0m < height < 2.0m) — requires jump
- **Wall** (height ≥ 2.0m) — impassable

Ground snapping uses a 0.12m standing tolerance and 0.3m falling tolerance, which is what makes the 0.42m drop from the landing onto the curved steps work without a bridge — the falling snap catches it. The split-level stairwell gap (1.8m wide) is sealed by enclosure walls that start at exact floor Y; previously a 2.125m wall offset let the player bypass collision entirely.

### The Staircase Problem

Rotated geometries produce inflated axis-aligned bounding boxes when measured via `Box3.setFromObject`. A 1.8m × 0.2m × 0.38m step rotated 45° produces a ~1.54m × 0.2m × 1.54m AABB — adjacent steps merge into a solid wall. The fix uses manual AABB computation from rotation cosines:

```js
const ca = Math.abs(Math.cos(angle));
const sa = Math.abs(Math.sin(angle));
const dX = halfW * ca + halfD * sa;
const dZ = halfW * sa + halfD * ca;
```

This fix was applied to all three curved flights (68 steps total), the east tower spiral (56 rotated treads), the library spiral, and the turret panels in `exterior.js`.

## Harness Engineering

> *"The harness is everything in the agent minus the model."* — Mitchell Hashimoto, February 2026

This project was built using the **harness engineering** paradigm — the discipline of designing the complete infrastructure surrounding an AI agent to make its outputs reliable at scale. The three pillars of harness engineering are guides, sensors, and architectural constraints. Here is how they map to this codebase:

### Pillar 1: Guides (Feedforward Controls)

| Guide | Implementation |
|---|---|
| **Architectural context file** | `PALACE_STATE.md` — a structured document injected at the start of every session containing floor dimensions, room registry, known issues, and the build order |
| **Structural decomposition** | The 20 prompts were not flat requests — each targeted a specific architectural subsystem with explicit constraints, references to prior work, and measurable acceptance criteria |
| **Module boundary enforcement** | ES module imports were the constraint — each room module could only access `scene`, `collisionWorld`, and `materials`; no cross-room dependencies were permitted |
| **State compact** | Each session began with a compressed summary of what existed and what remained, fitting within DeepSeek's 170K context window |

### Pillar 2: Sensors (Feedback Controls)

| Sensor | Implementation |
|---|---|
| **Live browser verification** | After each session, the agent's output was verified in-browser — walk through every floor, test every staircase, verify collision boundaries |
| **Debug room labels** | A tab-key debug overlay rendered room module names in-world, making it immediately visible if a module failed to load or misaligned |
| **NaN scrubbers** | `engine.js` contains automated NaN scrubbers that detect and neutralize corrupted vertex data at runtime (a sensor that catches what the model cannot self-correct) |
| **Collision grid validation** | The collision system normalizes box coordinates and filters degenerate boxes — a deterministic sensor that prevents malformed collision data from propagating |
| **Cache-busting audit** | In the final session, an automated grep-based audit identified every relative `import` that lacked `?v=2` and remediated all 58 occurrences across 27 files |

### Pillar 3: Architectural Constraints

| Constraint | Implementation |
|---|---|
| **No build tool** | Zero build dependencies — pure ES modules via importmap. This eliminated an entire class of agent failure modes (misconfigured bundlers, stale build caches, package version conflicts) |
| **Single collision world** | All modules register collision boxes into one global `CollisionWorld` instance — prevents room modules from creating independent, mutually-invisible collision spaces |
| **Procedural geometry primitives** | `geometry.js` defines `addWall`, `addFloor`, `addStep` as the only allowed primitives. The agent could not invent new geometry patterns — it composed from a constrained vocabulary |
| **Deterministic light registry** | All lights register into typed arrays (point, spot, directional, ambient) — no ad-hoc lighting. This made scene introspection possible via debug overlays |

### Why This Matters

Research demonstrates that changing only the harness configuration can improve agent solve rates by **64%** relative to baseline setups. The same model (DeepSeek V4 Flash) produces fundamentally different results depending on whether it operates through a harness or without one. This project was built with an explicit harness layer, not raw prompting.

The debugging session (session 20) is itself a harness artifact: each bug was diagnosed through structured interrogation (reproduce → isolate root cause → engineer permanent fix → verify fix holds across all instances), precisely following the Hashimoto discipline of making each mistake structurally impossible to repeat.

## Prompt Engineering

The system was not merely prompted — it was **programmed through context**. Each of the 20 prompts followed a precise structure:

1. **Architectural intent** — what to build and where
2. **Structural constraints** — module boundaries, collision rules, material references
3. **Prior state reference** — what existed from previous sessions
4. **Acceptance criteria** — how to verify the output was correct

This is prompt engineering elevated from *"what should I say"* to *"what system should I build"* — the transition from prompt engineering to harness engineering. The agent never produced regressions across sessions because the context file encoded architectural invariants that each new session was required to respect.

## Status

**Prototype — Beta quality.** This project was produced by an AI agent across 20 sessions with a single debugging pass. It works, but:

- Collision resolution is order-dependent (X resolved before Z) — corner cases may pinch the player
- NaN scrubbers in `engine.js` detect and neutralize vertex corruption but do not fix the upstream cause
- Some procedural geometry uses non-deterministic `Math.random()` — exact states are hard to reproduce
- Audio is tightly coupled to trigger positions (piano, wind near windows, water drip)
- Most materials have color maps only; normal and roughness maps are limited
- The project runs from `file://` protocol with no server — some browsers cache ES modules aggressively (mitigated by `?v=2` cache-busting on all imports)
